# ADR-0002: タイルベースキャンバス + LZ4 スワップ方式の採用

| 項目 | 値 |
|------|---|
| Status | Accepted |
| Date | 2026-05-27 |
| Deciders | 開発チーム |
| 関連 | requirements.md §6.2, §6.3, §6.4, architecture.md §5 |

## Context

Choco のメモリ予算は以下のとおり厳しい。

- 通常使用 ≤ 512MB、ピーク ≤ 1.0GB（Undo 履歴込み）
- 入力上限: 長辺 8192px、面積 16MP（4096×4096）
- レイヤー: 背景 + 編集 の 2 層

最大入力（8192×8192 相当を仮定）で RGBA 非圧縮データを 2 レイヤー単純保持すると:

```
8192 × 8192 × 4 byte × 2 layer = 約 512MB
```

ここに Undo 履歴・選択範囲 bitmap・OffscreenCanvas・JS/WASM の双方コピーが加わると 1GB 予算を確実に突破する。

加えて以下の操作要件がある:
- ブラシ操作: 60fps (16ms 予算)
- Flood Fill: 200ms 以内 (FHD)
- ズーム・パン: スムーズ

全画像をフラットな ImageBitmap として常駐させる単純実装では、メモリ・編集レイテンシ・Undo サイズすべてが破綻する。

## Decision

キャンバスを **256×256 ピクセルのタイル単位で分割管理** し、以下の戦略を採用する。

1. **可視タイルのみメモリ常駐**（resident set）。LRU で管理
2. 不可視タイル・最近未使用タイルは **LZ4_flex で圧縮し、`%TEMP%\choco\<session>\tiles\` に退避**（swap-out）
3. dirty tracking: タイル単位で「直近操作で変更されたか」フラグを保持し、Undo 記録と再描画範囲計算に活用
4. ブラシ・Flood Fill 等の操作は影響タイルのみ再計算・再描画

## Consequences

### 採用根拠

| 項目 | 効果 |
|------|------|
| メモリ削減 | LRU 上限 ※暫定 256 タイル = 64MB/レイヤー で運用可能 |
| Undo 効率 | 差分パッチをタイル単位で記録（ADR-0003 / architecture.md §6 と組み合わせ） |
| 再描画効率 | dirty タイルだけ Konva 再描画。FHD 全画面再描画より大幅高速 |
| 並列処理 | タイル境界で処理を分割、rayon でタイル並列化容易 |
| ディスク IO | LZ4 は圧縮・展開ともに非常に高速（数百MB/s 級）で、HDD の Min 機でも実用範囲 |

### タイルサイズを 256×256 にする根拠

| サイズ | 1 タイル | メリット | デメリット |
|--------|---------|---------|-----------|
| 64×64 | 16KB | 細かい dirty 単位 | タイル数増加でメタデータコスト・タイル間処理オーバヘッド大 |
| **256×256** | **256KB** | **CPU キャッシュ親和性・処理単位として手頃・業界標準** | 端タイル余白 |
| 1024×1024 | 4MB | スワップ単位として効率的 | dirty 単位が粗くメモリ無駄が多い、ブラシ操作で大きすぎる |

256×256 はゲーム業界のテクスチャ管理・タイルマップで広く使われるサイズ感で、CPU L2 キャッシュにも収まる。Konva の描画粒度や Web Worker への Transfer サイズとしても適切。

### LZ4 を選ぶ理由

| 圧縮方式 | 圧縮率 | 速度 | 採否 |
|---------|--------|------|------|
| **LZ4 (lz4_flex)** | 中（1.5-2.5x） | 非常に高速 (>500MB/s 圧縮 / >2GB/s 展開) | **採用** |
| zstd | 高（2-3x） | 高速だが LZ4 より遅い | 採用しない。Choco は速度優先 |
| deflate/gzip | 高 | 遅い | 不採用 |
| 無圧縮 | 1x | 最速 | ディスク IO・容量で不利、不採用 |

タイル退避時はユーザー操作中に発生する可能性があり、圧縮速度が UX に直結する。LZ4 の速度優位性が決定的。

### 採用しない代替案

1. **全画素フラット ImageBitmap 1 枚で保持** - メモリ予算超過。除外
2. **タイル化するがディスクスワップせず、メモリ圧縮のみ** - 8192px 画像で 2 レイヤー × LZ4 圧縮後でも 200MB+ となり、Undo 履歴・選択範囲を加えると 1GB に迫る。安全マージンが薄く除外
3. **タイル化 + OS 仮想メモリに任せる（明示的スワップなし）** - Windows ページファイル経由のスワップは細粒度制御が効かず、HDD 環境で UX が破綻する。明示制御で予測可能性を確保

### リスクと対策

| リスク | 対策 |
|--------|------|
| HDD Min 機でスワップ IO が遅い | LRU 上限を環境に応じて動的調整（M3 で実機計測、上限を低めにとり swap 発生頻度を抑制） |
| 一時ファイルの容量増加 | セッション ID 付きディレクトリで管理、起動時に古いセッションをクリーンアップ |
| クラッシュ時のゴミ残留 | アプリ起動時に古い `%TEMP%\choco\<session>\` を検出・削除 |
| タイル間継ぎ目アーチファクト | 描画時に隣接タイル参照、ブラシは複数タイルにまたがって 1 操作で描画 |
| 端タイルの幅・高さ非 256 | TileBuf 構造体で width/height を持ち、コードで一律対応 |

### 計測・調整項目（※要検証）

- LRU 上限タイル数の最適値（暫定 256、M3 で実機計測）
- スワップ閾値（不可視継続時間）
- LZ4 圧縮レベル（lz4_flex はレベル選択肢が限定的だが、可変なら検証）
- HDD Min 機での swap-out / swap-in レイテンシ

### タイル swap ID 生成規約（Sec-M1）

タイル swap ID は **Rust (Tauri Core) 側で UUIDv4 を生成し、JS には払い出されたものを返す** 設計とする。理由は以下のとおり。

- JS 側で ID を生成し Rust 側ファイルパスに連結する設計は、`../` 等を含むパストラバーサル攻撃の経路となるため不採用
- Rust 側で UUIDv4 を生成すれば、ID の値域がアプリ管理下で一意に閉じる
- セッションディレクトリ (`%TEMP%\choco\<session>\tiles\`) 配下にのみ書き込み、ファイルパス組み立ては Rust 内部で完結

JS から swap ID を Rust に渡すケース（swap-in 時など）でも、以下のバリデーションを Rust 側で必須化する。

- 文字列長 = 36（UUIDv4 標準形式）
- 正規表現 `^[0-9a-f]{8}-[0-9a-f]{4}-4[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$`
- セッションディレクトリ配下に対応ファイルが存在することを `canonicalize()` で確認し、シンボリックリンク等で外部参照される経路を遮断

Tauri command シグネチャは以下に確定する（architecture.md §4.5 と同期）。

```rust
#[tauri::command]
pub async fn swap_out_tile(rgba: Vec<u8>) -> Result<String, AppError> {
    // Rust 側で UUIDv4 を生成、lz4_flex 圧縮、tempfile に書出、swap_id を返す
}

#[tauri::command]
pub async fn swap_in_tile(swap_id: String) -> Result<Vec<u8>, AppError> {
    // 1. swap_id を UUIDv4 形式バリデーション
    // 2. セッションディレクトリ配下のパス組立
    // 3. canonicalize() で実体パスを確認
    // 4. 読み出し + lz4_flex 展開
}
```
