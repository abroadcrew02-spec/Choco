# ADR-0004: Layered SVG 出力方式（ラスター埋め込み + パス抽出）

| 項目 | 値 |
|------|---|
| Status | Accepted |
| Date | 2026-05-27 |
| Deciders | 開発チーム |
| 関連 | requirements.md §5.6, §6.2, architecture.md §3.4 |

## Context

要件 §5.6 で Layered SVG 出力が必須機能 (F12) として定義されている。出力構造の指定:

```xml
<svg>
  <image href="data:image/png;base64,..." />  <!-- 背景レイヤー -->
  <g id="edit-layer">
    <path fill="#FF0" d="..." />              <!-- 編集レイヤーの塗り範囲 -->
  </g>
</svg>
```

- 背景: 元画像をラスター埋め込み（base64 data URL）
- 編集レイヤー: 色域ごとにパスに変換
- 性能予算: Layered SVG 出力 (FHD) ≤ 2.0 秒

主ユースケース「ロゴ色変更」を考えると、Web 制作者が SVG を受け取ってさらに編集する可能性が高い。色ごとに分離されたパスが望ましい。

実装手法の選択肢:
1. **編集レイヤー全体をラスターのまま埋め込む** - 単純だが SVG にする意味が薄い
2. **編集レイヤーを色域ごとに連結成分分割 → 輪郭抽出 → SVG パス化**
3. **編集レイヤー全体をベクタトレース（vtracer 等）** - 元画像も含めて完全ベクタ化
4. **編集レイヤーを画素ごとに矩形 `<rect>` で出力** - 単純だが膨大なサイズになり破綻

## Decision

**手法 2: 編集レイヤーを色域ごとに連結成分分割 → 輪郭抽出 → SVG パス化** を採用する。

### 処理パイプライン

タイル単位ストリーミング集約方式を採る。全タイルを一括 RGBA 再結合してから WASM に渡す方式は、8192×8192 編集レイヤーで 256MB の中間バッファを要し WASM ヒープ上限 256MB を圧迫するため不採用とする（Perf-M1 指摘）。

```
編集レイヤーの全タイルを順次走査（WASM 側でタイル単位イテレータ）
    │
    ▼ 各タイル毎に処理
色域マップ更新 (RGBA 量子化なし、完全一致でグルーピング)
  - グローバルな color → タイル境界跨ぎマスクビルダー へ集約
    │
    ▼ 全タイル走査完了後
色ごとに 2値マスク (1bpp bitmap) を完成
  - マスク自体はタイル境界を意識しない平面ビットマップとして保持
  - 内部表現はタイル境界に沿ったランレングス or タイル分割マスクで省メモリ化
    │
    ▼
連結成分解析 (Connected Component Labeling)
  - 色ごとに独立して実行可能 (rayon でタイル並列化候補)
    │
    ▼
各連結成分の輪郭抽出 (Marching Squares または Suzuki-Abe)
    │
    ▼
ポリゴン → SVG パスデータ (M / L / Z コマンド)
    │
    ▼
（オプション）Douglas-Peucker でパス簡略化
    │
    ▼
背景レイヤーは PNG エンコード → base64 → <image>
    │
    ▼
SVG 文字列組み立て → ファイル書出
```

ストリーミング集約のメリット:

- 中間バッファのピークメモリを抑制（一度に全画素 RGBA を再結合しない）
- WASM ヒープ 256MB 上限 (要件 §6.4) との両立
- タイル単位の rayon 並列化との親和性が高い
- 早期 progress 通知が可能（SVG 出力 UI 進捗表示の M5 拡張）

## Consequences

### 採用根拠

- 主ユースケース（ロゴ色変更）と整合: 色ごとに `<path>` が分かれていれば、Illustrator / Inkscape / ブラウザ DevTools で色を差し替えられる
- 編集レイヤーは「塗りつぶし」「ブラシ」での操作結果が中心で、色数が少なくパス化が現実的（写真的な編集ではない）
- 背景はそのまま PNG 埋め込みなので、元画像の劣化なし
- 性能予算 2.0 秒は FHD 編集レイヤーで充分達成可能（連結成分解析 + 輪郭抽出は WASM 実装で 1 秒未満想定、※要検証）

### 採用しない代替案

#### 手法 1: 編集レイヤーをラスター埋め込みのみ

```xml
<svg>
  <image href="...background.png" />
  <image href="...edit.png" />  <!-- これだけ -->
</svg>
```

- メリット: 実装最小、PNG とほぼ等価で完全な見た目再現
- デメリット: SVG にする意味が薄い、色変更ができない、ファイルサイズが大きい
- → 要件 §5.6 のサンプル構造と乖離。**不採用**

#### 手法 3: vtracer 等で全体ベクタ化

- メリット: 完全ベクタ、スケーラブル
- デメリット: 写真的な元画像で破綻する、計算コスト大（2 秒予算厳しい）、出力サイズ予測困難
- スコープ: Phase 3 で「ベクタトレース付き SVG 出力」として将来構想（要件 §4.3）
- → MVP では **不採用**

#### 手法 4: 画素ごとの `<rect>` 出力

- FHD 編集レイヤーで最大 200 万 `<rect>` → ファイルサイズ数百 MB、レンダリング不可
- → **不採用**

### 実装詳細

#### 色域抽出戦略

- ブラシ・バケツで生成された編集レイヤーは、典型的に 1〜10 色程度の塗りが連続領域として存在
- 単純な「ピクセルの RGBA を辞書キーとしてグルーピング」で十分（量子化不要）
- 半透明（α が 0 と 255 以外）の塗りは fill-opacity 属性で SVG パスに保持
- 完全透明（α = 0）の画素はパスに含めない

#### 連結成分 + 輪郭抽出

| アルゴリズム | 選択 |
|------------|------|
| 連結成分: 2-pass Connected Component Labeling | imageproc クレートに実装あり、採用 |
| 輪郭: Marching Squares (細線 → 多角形化) | 実装が単純、滑らかな輪郭、採用 |
| 代替: Suzuki-Abe (Border following) | OpenCV 系で有名、imageproc にも類似実装。複雑な穴あき領域に強い。MVP は Marching Squares、必要に応じて差し替え（※要検証） |

#### パス簡略化（オプション）

Marching Squares は連続する単位線分を生成するため、Douglas-Peucker アルゴリズムで簡略化することでファイルサイズを削減できる。

- 簡略化閾値: 0.5px 程度（※要検証、視認劣化なしのレベル）
- MVP では未実装でも 2 秒予算は達成見込み。出力サイズ削減が必要になった時点で導入

#### SVG 出力形式

```xml
<?xml version="1.0" encoding="UTF-8"?>
<svg xmlns="http://www.w3.org/2000/svg"
     width="<W>" height="<H>"
     viewBox="0 0 <W> <H>">
  <!-- 背景レイヤー -->
  <image x="0" y="0" width="<W>" height="<H>"
         xlink:href="data:image/png;base64,<base64>"
         preserveAspectRatio="none" />

  <!-- 編集レイヤー -->
  <g id="edit-layer">
    <path fill="#RRGGBB" fill-opacity="<a>" d="M ... Z M ... Z" />
    <path fill="#RRGGBB" d="..." />
    ...
  </g>
</svg>
```

- 同色は単一 `<path>` に `M ... Z` を複数連結して集約
- 完全不透明 (α = 255) は `fill-opacity` 属性省略

### リスクと対策

| リスク | 対策 |
|--------|------|
| 色域が多すぎてパス数爆発 | 完全一致グルーピングで自然に集約。問題化したら色量子化（K-means 等）を Phase 2 で検討 |
| 輪郭がカクカク（256 タイル境界） | Marching Squares はタイル境界を意識せず全体走査するため問題なし |
| ファイルサイズ膨張 | Douglas-Peucker パス簡略化、出力時に gzip 推奨（クライアント側保存時の話） |
| 2.0 秒予算未達 | WASM + rayon でタイル並列化、Marching Squares 実装最適化（※M5 実機ベンチで検証） |
| アルファ値の精度損失 | 0/255 以外の α は fill-opacity で保持。255 段階は SVG 表現可能 |

### 影響範囲

- `crates/choco-wasm/src/path_extract.rs` 連結成分 + 輪郭抽出
- `crates/choco-wasm/src/lib.rs` `extract_paths` API
- `src/io/exporters/layeredSvg.ts` SVG 文字列組み立て + base64 エンコード
- `src/worker/compute.worker.ts` パイプライン全体の orchestrate

### 後続検討

- Phase 3 のベクタトレース付き SVG（vtracer 等）導入時はこの ADR を Superseded にして新 ADR を起票
- パス簡略化のデフォルト ON / OFF はユーザー設定として追加可能（MVP では含めない）
